# React Best Practices Refactor (React + Tailwind + Astro)

This skill ensures React code follows **modern best practices**, with a strong focus on **modularity, readability, and maintainability**, especially when refactoring code generated by tools like Lovable and adapting it for **AstroJS projects using Tailwind CSS**.

## When to use this skill

Use this skill when:
- A React `.tsx` file contains multiple components in a single file
- The user asks to refactor, organize, or clean up React code
- Code was generated by Lovable or another AI tool
- Preparing React components to be used inside an AstroJS project
- A page-level component mixes layout, logic, and UI concerns

Do NOT use this skill when:
- The file already follows a modular component structure
- The user only wants a small fix or explanation
- The code is not React or JSX-based

## How to use it

Follow these steps strictly:

### 1. Identify the page root

- Detect the **main page component** (e.g. `PromptPage`, `PromptView`)
- This component becomes the **entry point** of the feature

### 2. Split into single-responsibility components

- Each component must:
  - Have **one clear responsibility**
  - Be defined in **its own file**
  - Avoid mixing layout, state, and business logic

Examples:
- Layout sections → separate components
- Forms → separate components
- Lists and items → separate components
- Modals and dialogs → separate components

### 3. Enforce folder structure

All refactored components must follow this structure:

components/react/Prompt/
├── PromptPage.tsx // Page-level composition only
├── PromptHeader.tsx
├── PromptForm.tsx
├── PromptList.tsx
├── PromptItem.tsx
├── PromptFooter.tsx
├── hooks/
│ └── usePrompt.ts
├── types.ts
└── index.ts

Rules:
- Feature folder name (e.g. `Prompt`) is mandatory
- No deep or arbitrary nesting
- Shared logic goes in `hooks/`
- Shared types go in `types.ts`
- `index.ts` re-exports public components

### 4. Component file structure (MANDATORY)

Every React component file must follow this structure:

```tsx
// 1. External imports
import React from "react";

// 2. Internal imports
import type { Prompt } from "./types";

// 3. Types / Interfaces
interface PromptHeaderProps {
  title: string;
}

// 4. Component
export function PromptHeader({ title }: PromptHeaderProps) {
  return (
    <header className="border-b border-zinc-200 pb-4">
      <h1 className="text-xl font-semibold text-zinc-900">
        {title}
      </h1>
    </header>
  );
}
```

Rules:

- Tailwind CSS is mandatory
- No CSS files or styled-components
- Utility-first styling only
- Named exports only (no default export)
- Props must always be typed
- No anonymous components
- Avoid complex logic inside JSX

### 5. Page component responsibilities

- The page-level component (PromptPage.tsx) must:
- Only compose components
- Handle high-level state and orchestration
- Avoid large JSX blocks
- Never contain reusable UI logic

### 6. Tailwind CSS rules

Use semantic grouping of classes

Avoid duplicated utility patterns → extract components instead
- Do NOT use inline styles
- Do NOT define global CSS
- Prefer responsive and state variants (md:, hover:, focus:)

### 7. AstroJS compatibility rules

Components must be framework-agnostic (no Next.js APIs)

No server-only code
- Hooks must be client-safe
- Tailwind must work via Astro integration

### 8. Output rules

When refactoring:

- Always show the final folder structure
- Output each file separately
- Do NOT keep the original monolithic file
- Do NOT mix explanation inside code blocks

### Expected Output

- Modular React components
- Tailwind-only styling
- AstroJS-compatible code
- Clean, feature-based folder structure
